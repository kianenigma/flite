1//! FLITE / FRAME-LITE
2//!
3//! Polkadot-SDK's FRAME, but low on the dose of complexity, therefore lite.
4//!
5//! This is a an experimental library meant only for demonstration purposes, and is not meant for
6//! production use. Yet, it might influence the decision making to those who want to build
7//! **reusable** FRAME-based libraries.
8//!
9//! Put differently, this crate demonstrates a number of techniques that can be used to build more
10//! opinionated, yet simpler variants of FRAME.
11//!
12//! ## Techniques
13//!
14//! The main techniques used in this library are as follows:
15//!
16//! ### NOT Relying on `frame_system` (and `cumulus::parachain_system`).
17//!
18//! FRAME comes with an underrated macro: `#[pallet::disable_frame_system_supertrait_check]`. This
19//! macro enables a pallet to rely on a pallet other than `frame_system`. This opens the door for a
20//! team to write an "opinionated flavor" of `frame_system` for their own use.
21//!
22//! In this crate, we introduce [`flite_system`], an opinionated alternative to
23//! [`polkadot_sdk::frame_system`].
24//!
25//! ### Constrained Associated Types
26//!
27//! Constrained associated types are a powerful and an underrated feature of Rust, and they are
28//! crucially important for FRAME.
29//!
30//! FRAME expresses the majority of its flexibility through associated types. Constrained associated
31//! types are then therefore a way for one to express limitations on those associated types.
32//!
33//! The downside of this would be that the users would have less flexibility. Yet, the benefit would
34//! be that the syntax would be less generic, and more concrete.
35//!
36//! We argue that for a starter FRAME template, and for beginner users it is much easier to work
37//! with concrete types for common concepts like `AccountId` and `Balance`, rather than generic
38//! variants.
39//!
40//! ```rust
41//! trait Currency {
42//!     type Balance;
43//!
44//!     fn get() -> Balance {};
45//! }
46//!
47//! /// A pallet that is not constraining `Currency::Balance`, and must always refer to it as
48//! trait Config {
49//!     type Currency: Currency
50//!
51//!     fn usage() {
52//!         // This pallet doesn't really now what `<Self::Currency as Currency>::Balance` is.
53//!         let _: <Self::Currency as Currency>::Balance = T::Currency::get();
54//!     }
55//! }
56//!
57//! /// A pallet that is constraining `Currency::Balance`, to JUST `u128`.
58//! trait Config {
59//!     type Currency: Currency<Balance = u128>;
60//!
61//!     fn usage() {
62//!         // This pallet knows that `Self::Currency::Balance` is `u128`.
63//!         let _: u128 = T::Currency::get();
64//!     }
65//! }
66//! ```
67//!
68//! [`flite_system`] constraints a number of important associated types, to be seen in the example
69//! further below.
70//!
71//! ### Tight Coupling To Our Benefit
72//!
73//! Generally, [tight
74//! coupling](https://paritytech.github.io/polkadot-sdk/master/polkadot_sdk_docs/reference_docs/frame_pallet_coupling/index.html)
75//! is considered a bad thing. Yet, in the context of a library like `flite`, we can use it to our
76//! advantage. If we tightly couple [`flite_system`] with a number of pallets, we achieve:
77//!
78//! * We can express that a runtime can only work if [`flite_system`] and the tightly coupled
79//!   pallets are present in it.
80//! * We can safely provide a set of default for all the configurations of the tightly coupled
81//!   pallets.
82//! * We can also express constrains on the configurations as constraints on the associated types,
83//!   as explained above.
84//!
85//! ### Example: `flite_system`
86//!
87//! With the above context in mind, let's look and analyze [`flite_system::Config`], which puts all
88//! of the above practices in one place.
89#![doc = docify::embed!("./src/lib.rs", FliteSystemConfigExport)]
90//!
91//! Notice how `flite` is constraining the `AccountId` to be [`types::AccountId`], the `Balance` to
92//! be [`types::Balance`], and even more advance things like `HoldReason`.
93//!
94//! This means `flite_system` can only be used in a runtime with such constants. More nicely, a
95//! pallet using `flite_system` can already be written with these concrete types in mind.
96//!

110//! abstractions. These are discussed in [`native_currency`].

112//! First, a pallet can import and use FRAME's currency abstractions in the *old school* way. That
113//! is, pull the currency abstractions via `trait Config`:

116//! And then use them as such:

122//! `u8`. All of this is because [`flite_system`] has already constrained these types.
123//!
124//! `flite` can also provide even simpler, even more opinionated currency abstractions, such as
125//! [`native_currency::Simple`]. The usage of such a simple abstraction can look like:
126#![doc = docify::embed!("../simple-pallet/src/lib.rs", simple_currency_usage)]
127//!
128//! ### A Step Further: Defaults For Tightly Coupled Pallets
129//!
130//! As the final step, `flite` could also simplify the process of runtime configuration, if it could
131//! provide defaults for all the pallets that it is tightly coupling itself with.
132//!
133//! All of these defaults can be audited and guaranteed to work nicely together, as long as none of
134//! them is tweaked by the end user. If a mild degree of flexibility is needed, we instead provide a
135//! separate, higher level trait that can be used to parameterize all other pallets with.
136//!
137//! In [`default_configs`], we provide one such example. The end-user entry-point is merely
138//! [`default_configs::FliteConfigurations`]. This is one trait that we expect the end user to
139//! parameterize for us. Instead of a lot of the technical nitty-gritty details that
140//! [`polkadot_sdk::frame_system`] exposes, this trait is meant to be very easy to comprehend to a
141//! novice developer.
142//!
143//! Then, based on `FliteConfigurations`, we provide defaults for each pallet's `Config` traits:
144//!
145//! - [`struct@default_configs::FliteFrameSystem`]
146//! - [`struct@default_configs::FliteTimestamp`]
147//! - [`struct@default_configs::FliteAura`]
148//! - [`struct@default_configs::FliteBalances`]
149//!
150//! > These defaults are provided in a format that should be compatible with `FRAME`'s native
151//! > `derive_impl` (or the underlying `macro_magic` crate), yet this part is not yet working in
152//! > this demo and therefore the runtime file contains a lot of boilerplate.
153//!
154//! Notice how all of these types are generic over `F`, which is a [`FliteConfigurations`].
155//!
156//! This technique allows us to retain some degree fo flexibility, and abstract over complicated
157//! relationships. For example, (almost) all runtimes have
158//! [`polkadot_sdk::pallet_timestamp::Config::MinimumPeriod`] set to half of
159//! [`polkadot_sdk::pallet_aura::Config::SlotDuration`]. We abstract over this needless complication
160//! by providing one simple configuration to the user [`FliteConfigurations::BlockTime`] (which is
161//! what we mean by `SlotDuration`). Under the hood, we take care of providing the correct defaults
162//! to each of the aforementioned pallets.
163//!
164//!
165//! ## Further Ideas
166//!
167//! - Create abstractions over [`polkadot_sdk::pallet_assets`], and the
168//!   [`polkadot_sdk::polkadot_sdk_frame::traits::fungibles`] as well, for example hardcoding the
169//!   `AssetId` to be `u32`.
170//! - More pallets that are reasonable always needed: `authorship`, `session`, etc.
171//! - `flite`, and `flite-parachain`. If one has to be chosen, we care more about parachain.
172//! - `flite` can provide a single set of weights that are safe to use in [`weights`].
173//! - [`flite_system::Pallet`] can provide further standalone helper functions, such as
174//!   [`flite_system::Pallet::block_author`].
175//! - `integrity_test` in `flite_system` is super important, as it is the one place where we can
176//!   check the configuration of all pallets. For example, the relationship between `BlockTime`,
177//!   `SlotDuration` and `MinimumPeriod` can be expressed here. The ability to check these within a
178//!   pallet is yet another benefit of tight coupling.
179//!
180//! ## Reflection
181//!
182//! - Everything here is backwards compatible, and a developer who is advance can always fallback
183//!   into the ADVANCE-FRAME-land.
184//! - One of the downsides of this approach is that the flite-based runtime is noticeably slower to
185//!   compile due to the excessive use of macros.

457	/// A simple native currency abstraction.
458	pub struct Simple<T: flite_system::Config>(core::marker::PhantomData<T>);
459	impl<T: flite_system::Config> Simple<T> {
460		/// Flite can go down the path of providing its own wrappers around the FRAME advanced
461		/// currency system.
462		pub fn balance_of(account: &types::AccountId) -> types::Balance {
463			<psdk::pallet_balances::Pallet<T> as fungible::Inspect<types::AccountId>>::balance(
464				account,
465			)
466		}
467
468		pub fn transfer(
469			from: &types::AccountId,
470			to: &types::AccountId,
471			amount: types::Balance,
472		) -> DispatchResult {
473			<psdk::pallet_balances::Pallet<T> as fungible::Mutate<types::AccountId>>::transfer(
474				from,
475				to,
476				amount,
477				frame::traits::tokens::Preservation::Expendable,
478			)
479			.map(|_| ())
480		}
481
482		pub fn lock(from: &types::AccountId, amount: types::Balance) -> DispatchResult {
483			<psdk::pallet_balances::Pallet<T> as fungible::MutateHold<types::AccountId>>::hold(
484				&0u8, from, amount,
485			)
486		}
487	}
